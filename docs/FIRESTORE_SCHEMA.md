# Firestore schema

This is the FB-04 storage and query contract for the nine top-level collections. It maps to the CORE-04 Kotlin models and specifies what future repositories, trusted operations, and Security Rules must enforce. The checked-in `firestore.rules` currently denies all client reads and writes. Index definitions grant no access and have not been deployed.

## Field and timestamp conventions

- Kotlin `id: String` maps to the document ID. Foreign keys are string document IDs. Stored enum names are case-sensitive strings.
- Required fields must be present and non-null. Optional values may be omitted or null, and map to Kotlin null. Empty question tags are stored as an empty array. Other defaults are creation-time values set by authorized writers, never fallbacks for missing security fields on reads.
- All audit timestamps are Firestore timestamps generated by the server. Set `createdAt` once. Where `updatedAt` exists, initialize it on creation and refresh it on committed state changes, including changes to managed counters. An idempotent no-op leaves timestamps unchanged. `startsAt` and `endsAt` are scheduled event times, not audit timestamps.
- Map timestamps explicitly to `java.time.Instant`, Firestore integers to the corresponding Kotlin `Long` or checked `Int`, and unknown enums or malformed required values to a mapping error. Do not infer a role, status, counter, or timestamp from an incomplete record.

## Document IDs

- `users/{uid}` uses the authenticated Firebase Auth UID. `schools`, `programs`, `activities`, `questions`, `answers`, and `reports` get a generated document ID once on creation. IDs remain stable across edits.
- `enrollments` uses the ordered pair `(activityId, studentId)`. `answerVotes` uses `(answerId, userId)`. Encode both as `v1.<base64url(parentId)>.<base64url(uid)>` using unpadded base64url over the exact UTF-8 bytes of each nonempty ID. The period cannot occur inside either encoded component. Never trim, normalize, or change the case of the input IDs.
- The encoding avoids delimiter collisions and Firestore path separators. It is reversible and expands the inputs, so reject an encoded ID over Firestore's 1,500-byte limit. Only the writer's canonical ID is valid. A trusted write must derive the actor from Auth, verify the referenced parent and participant where applicable, and use that canonical path. The ID scheme alone cannot enforce uniqueness if alternate paths are writable. [Firestore ID limits](https://firebase.google.com/docs/firestore/quotas#collections_documents_and_fields)

## Collections

| Collection / model | Required fields and Firestore types | Optional fields and Firestore types | Creation defaults |
| --- | --- | --- | --- |
| `users` / `UserProfile` | `displayName`, `email`, `role`, `status` (string); `createdAt`, `updatedAt` (timestamp) | `schoolId`, `programId`, `phone` (string) | Self-registration assigns `HIGHSCHOOL_STUDENT` on the server. Trusted provisioning chooses other roles. New approved accounts start `ACTIVE`. |
| `schools` / `School` | `name`, `city`, `description` (string); `createdAt`, `updatedAt` (timestamp) | `website` (string) | No status or additional defaults. |
| `programs` / `Program` | `schoolId`, `title`, `description` (string); `createdAt`, `updatedAt` (timestamp) | None | No status or additional defaults. |
| `activities` / `PromoActivity` | `schoolId`, `authorId`, `title`, `description`, `type`, `location`, `status` (string); `startsAt`, `endsAt`, `createdAt`, `updatedAt` (timestamp); `capacity`, `cost`, `reservedSeatCount` (integer) | `visitCount` (integer) | `PUBLISHED`, `reservedSeatCount = 0`. Supply cost explicitly, with zero for a free event. |
| `enrollments` / `Enrollment` | `activityId`, `studentId`, `status` (string); `createdAt`, `updatedAt` (timestamp) | `cancellationReason`, `completionNote` (string) | `ACTIVE`, both notes absent. |
| `questions` / `Question` | `authorId`, `title`, `body`, `status` (string); `tags` (array of strings); `createdAt`, `updatedAt` (timestamp); `publishedAnswerCount` (integer) | `schoolId`, `acceptedAnswerId` (string) | `PUBLISHED`, `tags = []` if none supplied, `publishedAnswerCount = 0`. |
| `answers` / `Answer` | `questionId`, `authorId`, `body`, `status` (string); `createdAt`, `updatedAt` (timestamp); `upvoteCount` (integer) | None | `PUBLISHED`, `upvoteCount = 0`. |
| `answerVotes` / `AnswerVote` | `answerId`, `userId` (string); `value` (integer, exactly `1`); `createdAt` (timestamp) | None | Presence represents one upvote. Removal deletes the document, and adding again creates a new vote with a new `createdAt`. |
| `reports` / `ContentReport` | `reporterId`, `targetType`, `targetId`, `reason`, `status` (string); `createdAt`, `updatedAt` (timestamp) | None | `OPEN`. Submission has no effect on target visibility. |

Firestore `activities.cost` maps to Kotlin `costMinorUnits: Long` and holds RSD minor units. `capacity` and `visitCount` map to Kotlin `Int`. Activity types are `FAIR`, `SCHOOL_TOUR`, and `WORKSHOP`. Report target types are `QUESTION` and `ANSWER`. Store tags trimmed and case-folded consistently with query inputs. The three counters and `updatedAt` on users and reports are storage-only fields in this contract.

## Status transitions

| Collection | Permitted transitions |
| --- | --- |
| `users` | `ACTIVE` ↔ `BANNED` through a trusted admin action. Role and school reassignment also require trusted admin authorization. |
| `activities` | `PUBLISHED` → `CANCELLED` or `REMOVED`, and `CANCELLED` → `REMOVED`, by an admin or a professor assigned to that school. `REMOVED` is terminal. Past events are determined by `endsAt`. |
| `enrollments` | `ACTIVE` → `CANCELLED` or `COMPLETED`. Self-cancellation requires a reason. Self-completion requires a note, server time at or after `endsAt`, and an event that remains `PUBLISHED`. Authorized roster removal cancels an active record. `CANCELLED` → `ACTIVE` requires an eligible participant, a published activity before `startsAt`, and an available seat. `COMPLETED` is terminal. |
| `questions`, `answers` | `PUBLISHED` → `HIDDEN` for admin moderation. Author deletion of an answer also uses `HIDDEN` to preserve references. Restoration is outside the MVP contract. |
| `reports` | `OPEN` → `RESOLVED` or `DISMISSED`, by an admin. Both are terminal. |

Schools, programs, and votes have no status field. Reapplying updates the same enrollment, keeps its original `createdAt`, refreshes `updatedAt`, and clears prior cancellation/completion notes. Repeat application to an already active record leaves it unchanged. This design stores the latest enrollment state and does not preserve a full attempt or transition history. A separate audit mechanism would be required for that history.

## Relationships and future authorization

| Active role | Role-specific permissions |
| --- | --- |
| `ADMIN` | Manage accounts, schools and programs, activities, rosters, and moderation. Privileged account provisioning and status changes require a trusted administrative operation. |
| `PROFESSOR` | Manage activities and rosters only for the school assigned in the trusted profile. Create answers and edit or delete own answers. |
| `STUDENT` | Existing university student. Primarily answers questions and can edit or delete own answers. Retains the existing eligible self-enrollment path. |
| `HIGHSCHOOL_STUDENT` | Prospective student and the primary audience for open days, workshops, and other educational events. Can self-enroll when eligible, manage own enrollments, create and edit own questions, and choose accepted answers on own questions. |

All active roles may read the authorized catalog, published activities, and visible forum content, edit their own `displayName` and `phone`, set their own upvote, and submit and view their own reports. Enrollment ownership stays under Firebase Auth. The existing `studentId` field is the enrolled participant's UID, not a requirement that their role be `STUDENT`. For self-service operations the backend uses the verified Auth UID. Administrative participant methods may name a target user and must authorize the actor and check the target's eligibility independently.

- **Identity and catalog.** User school/program IDs reference the catalog. If both are present, the program must belong to the school. A program's school cannot be changed by an edit. Block catalog deletion while referenced. Full user documents are private to the owner and authorized admins. Resolve forum author names through an authenticated trusted projection that returns only `displayName`. Firestore rules grant reads at the document level. Passwords stay in Auth. [Firestore field access](https://firebase.google.com/docs/firestore/security/rules-fields)
- **Activities and enrollments.** Activities reference a school and an author. The server derives a professor's school from the trusted profile and sets the author from Auth. Enrollments reference an activity and a user. Roster reads require an owning-school professor or admin, while participants may read only their own records. Keep activity IDs and references after cancellation or soft removal. These statuses close new enrollments and reactivations while retaining existing enrollment records.
- **Forum and moderation.** Questions reference an author, optionally a school, and optionally an answer to that same question. Answers reference a question and author. Public answer reads require a visible parent question. Votes reference an answer and voter, and only the caller's vote state and authorized totals are exposed. Reports reference a reporter and a target resolved using `targetType`. Keep hidden content as a tombstone for reports. Only admins may read other users' reports or decide them.
- **Enforcement boundary.** Future access checks must enforce account status, role, relationship scope, owner identity, and field allowlists in rules or a trusted backend. Clients cannot directly change role, school assignment, account status, ownership fields, or counters. Security Rules evaluate the potential query result set. Repositories must constrain queries to match the eventual rules. Server SDKs bypass those rules, so trusted endpoints must enforce their own authorization. [Firestore rules and queries](https://firebase.google.com/docs/firestore/security/rules-query)

## Data integrity and trusted transactions

| Operation | Required enforcement |
| --- | --- |
| Create/edit activity or change capacity | Trusted validation requires `startsAt < endsAt`, `capacity > 0`, and `cost >= 0`. A capacity edit must use the same activity transaction boundary as enrollment and never set capacity below `reservedSeatCount`. |
| Apply, add, reactivate, cancel, remove, complete | In a trusted transaction, read the parent activity and canonical enrollment, verify actor scope, participant eligibility, event timing and status, notes, and the previous state. Create or reactivate only below capacity and increment `reservedSeatCount`. Cancelling an active enrollment decrements it. Completion retains the consumed seat, so the counter equals active plus completed enrollments. Repeated requests must not double-adjust the counter. |
| Add/remove upvote | In a trusted transaction, verify the visible answer and parent, then create/delete the caller's canonical vote and adjust `upvoteCount` only when presence changes. |
| Publish, hide, or delete answer | In a trusted transaction, update the answer and change its question's `publishedAnswerCount` only when answer visibility changes. If a hidden answer was accepted, clear `acceptedAnswerId` in the same transaction. |
| Choose accepted answer | In a trusted transaction, verify question ownership and that the answer is published and belongs to the question before storing the reference. |
| Maintain references and status | Validate referenced documents and scope in trusted operations. Coordinate catalog deletion with reference creation to prevent dangling references. Keep soft-removed activity and forum documents for historical references. Privileged status changes must validate the recorded state and the authenticated actor. |

The three counters are nonnegative backend-owned integers. Future client-facing write rules must reject direct edits to them. Updating records and counters together avoids capacity races and count drift. Repository interfaces describe operations and do not implement these checks.

## MVP queries and indexes

All queries below are collection-scoped. Equality keys are listed first in each composite index. `↑` is ascending, `↓` is descending, and `ARRAY` is `arrayConfig: CONTAINS`. Add document ID as the final order field, in the direction of the last explicit sort. Firestore's implicit `__name__` index field already uses that direction. [Firestore index ordering](https://firebase.google.com/docs/firestore/query-data/index-overview#default_ordering_and_the_name_field)

| Collection | MVP query and filters | Composite index in `firestore.indexes.json` |
| --- | --- | --- |
| `activities` | Shared signed-in feed, `status = PUBLISHED`, date order | `status ↑, startsAt ↑` |
| `activities` | Published feed filtered by school | `status ↑, schoolId ↑, startsAt ↑` |
| `activities` | Published feed filtered by activity type | `status ↑, type ↑, startsAt ↑` |
| `activities` | Published feed filtered by school and type together | `status ↑, schoolId ↑, type ↑, startsAt ↑` |
| `activities` | Professor's own school management list across statuses | `schoolId ↑, startsAt ↑` |
| `questions` | Published questions, newest first | `status ↑, createdAt ↓` |
| `questions` | Published questions filtered by school | `status ↑, schoolId ↑, createdAt ↓` |
| `questions` | Published questions filtered by one tag with `array-contains` | `status ↑, tags ARRAY, createdAt ↓` |
| `questions` | Published questions filtered by school and one tag | `status ↑, schoolId ↑, tags ARRAY, createdAt ↓` |
| `answers` | Published answers by question, newest first | `questionId ↑, status ↑, createdAt ↓` |
| `answers` | Published answers by question, most helpful first | `questionId ↑, status ↑, upvoteCount ↓, createdAt ↓` |
| `enrollments` | Own enrollments filtered by the session UID in `studentId`, recently updated first | `studentId ↑, updatedAt ↓` |
| `enrollments` | Authorized roster filtered by activity, recently updated first | `activityId ↑, updatedAt ↓` |
| `reports` | Admin moderation queue, `status = OPEN`, oldest first | `status ↑, createdAt ↑` |
| `reports` | Own reports filtered by the session UID in `reporterId`, newest first | `reporterId ↑, createdAt ↓` |
| `programs` | Catalog filtered by school, title order | `schoolId ↑, title ↑` |

Activity date bounds use `startsAt >= startsFrom` and `startsAt < startsBefore` with the same indexes above, including the combined school/type shape. The professor's school filter comes from the trusted profile. A professor filtering by status can reuse the status-and-school index with that authorized status. Direct document reads, the own-vote lookup by canonical ID, and single-field catalog or admin sorts need no additional composite index. Answer vote totals come from `answers.upvoteCount`, and question card totals come from `questions.publishedAnswerCount`.

### Pagination and search

Use `limit(25)` for ordered lists. Start the next page after the last fetched document in the identical filter and sort scope. Use the document snapshot or the full sort tuple including document ID. Reset the cursor when filters change, and deduplicate by ID when mutable sort keys move documents between pages. The current `List`-returning interfaces support the initial bounded page. When a feature needs more pages, add a Firebase-independent cursor to its contract. [Firestore query cursors](https://firebase.google.com/docs/firestore/query-data/query-cursors)

MVP text search is case-insensitive local matching over **currently loaded, authorized results only**. An empty result means no match in those results, not in the entire database. School, type, date, and tag filters still run server-side. If further pages are loaded, advance from the last fetched document even when local text filtering hides it. The documented queries do not implement database-wide full-text or arbitrary substring search.

## Kotlin alignment and verification limits

The nine models and existing repository signatures remain valid. Enrollment self-service already has no caller-supplied user ID. The protected storage-only fields can be mapped separately when feature read models need them. The index file defines local configuration for later deployment. The emulator does not enforce composite index requirements, so JSON and query-shape validation cannot establish cloud query behavior. [Firestore emulator limitations](https://firebase.google.com/docs/emulator-suite/connect_firestore#how_the_cloud_firestore_emulator_differs_from_production)
